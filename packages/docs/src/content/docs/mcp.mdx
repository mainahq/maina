maina's MCP (Model Context Protocol) server gives any MCP client maina's verification, context and review tools.

:::tip[Using Claude Code, Cursor or Codex?]
Install the plugin instead: see [Install](/install/). The plugin adds the same MCP server plus the gate's hooks, the skills and the stop check. An MCP entry on its own gives the agent the tools and nothing else.
:::

## Setup

The fastest path is one command — it auto-detects every supported client on your machine and writes the maina entry into each global config:

```bash
maina mcp add
```

To remove maina from every client just as quickly:

```bash
maina mcp remove
```

Or scope to specific clients:

```bash
maina mcp add --client claude,cursor,windsurf
maina mcp add --scope project          # write the repo's files (.mcp.json, .cursor/mcp.json) instead of global
maina mcp add --dry-run                # preview the writes without touching disk
maina mcp list                         # show install status per client
```

Auto-detected clients: **Claude Code, Cline, Codex, Continue, Cursor, Gemini CLI, Windsurf and Zed**. Any other MCP client works with a manual entry (below). Each entry goes into the file the client actually reads — for Claude Code that is `~/.claude.json` (global) or `.mcp.json` (project), never `settings.json`. The command preserves all other MCP servers and unrelated keys (hooks, permissions, comments in Codex's TOML) via an atomic merge, backs the original up once under `.maina/backups/`, and is safe to run repeatedly. `maina mcp remove` restores the pre-maina file exactly when nothing else changed since, deletes a file maina created, and otherwise removes only the `maina` entry.

The launcher is auto-detected per machine, in this priority order:

1. **The installed CLI itself** when you run `maina mcp add` / `maina setup` from a global install (`bun install -g @mainahq/cli` or `npm install -g @mainahq/cli`): the entry is the runtime and the CLI entry file, both by absolute path (`/Users/.../.bun/bin/bun /Users/.../@mainahq/cli/dist/index.js --mcp`). Fastest by far — no package manager and no shebang in the spawn path, so it starts even when the client's PATH has no Bun or Node. **Recommended.**
2. **Direct `maina` binary** when one is on PATH but the command ran from a throwaway copy (e.g. `bunx @mainahq/cli setup`).
3. **Resolved `bunx @mainahq/cli@<version> --mcp`** when [Bun](https://bun.sh) is available.
4. **Resolved `npx @mainahq/cli@<version> --mcp`** as the universal fallback.
5. **Bare `npx @mainahq/cli@<version> --mcp`** as the last-resort fallback when nothing else resolves on the install machine — entry stays syntactically valid; user can edit after installing Node or Bun.

Tiers 1-4 are written using **absolute** paths (`/opt/homebrew/bin/bunx`, `/Users/.../.bun/bin/maina`, etc.) so MCP clients with stripped-PATH spawn contexts (Cursor, Zed, Claude Code desktop) can find them. Tier 5 is the only case where the bare command name is written. `<version>` is the version of the CLI that wrote the entry. Manual examples below use `npx` for portability.

The setup wizard (`maina setup`) also writes the project-scoped configs (`.mcp.json`, `.cursor/mcp.json`) for you using a **keyed JSON merge** — every existing `mcpServers.*` entry is preserved byte-for-byte and only the `maina` key is written — and registers maina in the global config of installed clients that have no project file (Codex, Windsurf, Zed, …). Safe to re-run; safe against hand-edited configs. The `curl … | bash` installer only installs the package and runs `maina setup`; it writes no config itself. Most users won't need `maina mcp add` unless they want maina available in every project from any client.

## Tools

The server registers a small default set at handshake, so the capability payload every session streams to the host stays small. The [MCP tools reference](/reference/mcp-tools/) lists every tool, generated from the server's catalog, and which ones need the allow-list.

Every tool also takes an optional `root`: the absolute path of the repository to act on. Without it the server uses the root it resolves for itself, normally the repository it was started in (the standalone runtime also honours the project dir the host reports). Relative `files` and `paths` resolve against the root, and absolute ones must sit inside it.

Every tool answers with a text summary for the model plus structured content in a `{ data, error, meta }` envelope, described by the tool's output schema:

<Code lang="json" code={`{
  "data": { "passed": true, "tools": [{ "tool": "semgrep", "status": "skipped", "findings": 0, "durationMs": 0, "reason": "semgrep is not installed" }] },
  "error": null,
  "meta": { "tool": "verify", "root": "/repo", "version": "${facts.version}", "durationMs": 812 }
}`} />

A failed call sets `isError`, `data: null` and `error: { kind, message }`, where `kind` is `no_root`, `invalid_input`, `not_found` or `failed`.

### Allow-list

Narrow the tool set, or add the DeepWiki-compatible tools, with the `--tools` flag or the `MAINA_MCP_TOOLS` env var (the flag wins). Names are comma-separated; `default` stands for the default set:

```bash
maina --mcp --tools verify,context,status        # only these three
MAINA_MCP_TOOLS=default,ask_question maina --mcp  # the default set plus ask_question
```

Tools outside the list are never registered. Unknown names are skipped with a warning on stderr.

## How it works

The MCP server is a thin surface over the same capabilities the CLI uses: each tool resolves its root, calls one capability with explicit inputs, and formats the answer. It speaks JSON-RPC over stdio, started by the client as `maina --mcp`.
