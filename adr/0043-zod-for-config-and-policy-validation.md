# 0043. Zod for config and policy validation

Date: 2026-09-25

## Status

Accepted

## Context

The v1 rebuild (mainahq/maina#365) turns Maina into a gate that decides whether an agent action is allowed, asked or denied. That gate reads two user-authored files. The first is the project config, `.maina/config.json`: models, provider, budget and the keys 1.x already writes there. The second is the gate policy, `.maina/policy.json`, layered over a user default: action classes, rule lists, decision backends and thresholds, drift thresholds and telemetry opt-ins.

Task 1.4 (mainahq/maina#293, FR-GATE-9) requires that:

- an invalid file returns every error with its path, not just the first;
- the published JSON Schemas are generated and match the TypeScript types;
- the loaders are pure: they read through the `fs` port and return a `Result` instead of throwing.

In 1.x, config was a `maina.config.ts` module that was imported dynamically and shallow-merged over the defaults with no validation. A typo in a nested key silently replaced the whole nested object, and the `budget` block was never read by anything.

Options considered:

1. **Hand-written validators and a hand-written JSON Schema.** Rejected. That gives three sources of truth (TS types, validator, schema) that drift apart, and it breaks the "one source of truth" rule.
2. **JSON Schema first, with a validator (Ajv) and generated TS types.** Rejected. It needs a codegen step for the types, adds Ajv and its dependency tree to `@mainahq/core`, and its error paths are JSON Pointers that need their own formatting.
3. **TypeBox.** Viable, since it emits JSON Schema natively. Rejected because it would be a second schema library next to zod, which `@mainahq/mcp` already uses for tool inputs.
4. **Zod 4.** Chosen. It is already a workspace dependency (`@mainahq/mcp`, `^4.3.6`). Types are inferred with `z.infer`, JSON Schema comes from the built-in `z.toJSONSchema` with no extra package, `safeParse` collects every issue with a structured path without throwing, and strict objects reject unknown keys, which catches typos.

## Decision

- `@mainahq/core` depends on `zod`. The zod schemas in `packages/core/src/config/schema.ts` and `packages/core/src/policy/schema.ts` are the only definition of the config and policy shapes. `Config`, `ConfigLayer`, `Policy` and `PolicyLayer` are inferred from them.
- `schemas/maina.config.schema.json` and `schemas/policy.schema.json` are generated by `bun run schemas:generate` (`scripts/generate-schemas.ts`) and committed. A core test and `bun run schemas:check` fail when a committed file differs from what the schema generates.
- File schemas are strict (unknown keys are errors) and every key is optional. The loaders merge a validated layer over the defaults with a defined merge (nested objects key by key; policy rule lists accumulate) instead of a shallow spread.
- Validation errors are `{ kind, file, path, message }` values. `path` is dotted (`budget.dailyUsd`, `rules.deny[0].match`), and `""` means the root or the whole file.
- Config keeps the camelCase keys 1.x used. Policy is a new file, so it uses the snake_case names the spec gives it (`explicitly_allow`, `action_classes`).

## Consequences

### Positive

- One definition gives the runtime validation, the TS types, and the schema editors use for completion (`"$schema": "../schemas/policy.schema.json"`).
- Users see every mistake in one pass, each with its location.
- The loaders stay pure and testable with the in-memory `fs` fake.

### Negative

- `@mainahq/core` gains a runtime dependency, though zod has no transitive dependencies.
- The shape of the generated JSON Schema follows zod's `toJSONSchema` output. A zod upgrade can change it, and then the generated files have to be regenerated and reviewed.
- The 1.x `budget.daily/perTask/alertAt` keys are now rejected in `.maina/config.json`. The 1.x `maina.config.ts` loader (`loadConfigModule`) maps `daily`/`perTask` onto `dailyUsd`/`perTaskUsd` until the migration task (mainahq/maina#301) replaces it.
